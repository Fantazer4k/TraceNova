# TraceNova — план доведения до релиза

Срез от 22 ноября 2026 года. База плана — `repair/main-security`, коммит `89f1d61`. [ISSUES.txt](ISSUES.txt) содержит текущий статус работ и проверок. [SECURITY_REVIEW.md](SECURITY_REVIEW.md) содержит предыдущие срезы аудита.

## Результат и границы

Первый результат — воспроизводимая локальная сборка с понятными статусами всех шести режимов и проверенным браузерным интерфейсом. Второй — закрытый стенд с управлением доступом, квотами, наблюдаемостью и проверенным откатом. Внешняя публикация зависит от решения владельца и прохождения ворот релиза.

Последняя проверка ветки зафиксировала 36 Python-тестов, JS-проверку шести рендереров, успешный `pip check` и отсутствие известных уязвимостей по `pip-audit` в установленном дереве Python 3.13.13. В этом проходе сверены список файлов, кодовые точки входа, документы и реестр. CI, браузер и внешние интеграции требуют отдельной верификации. Отдельных пользовательских записей вне перечисленных строк `ISSUES.txt` в рабочем дереве на момент проверки не обнаружено.

### API и хранение

Сохранить `POST /api/analyze` и текущие поля. В F2 сначала закрепить словарь статусов и их значение, затем добавить совместимые поля результатов в сервисах и отрисовать их в UI. Примеры должны показывать одновременно данные источников, статус покрытия и ошибку провайдера. Квоты для нескольких воркеров хранит выбранный шлюз или его штатное хранилище. SQLite-кэш остаётся выключенным. Если появится требование сохранять историю, отдельное решение должно определить разрешения, срок хранения, удаление и миграцию схемы.

Окна предполагают параллельную работу Backend, Platform и Frontend/QA. Суммарный объём — 15–28 человеко-дней. При одном исполнителе и отсутствии ожиданий ориентир — 3–6 рабочих недель. Критический путь для внешнего релиза проходит через решение о контуре, R2/R3/N1, проверку релизной сборки R1 и приёмку Q1/O1. Время получения доступов оценивается отдельно.

## Каденция

Обновлять ISSUES.txt после каждого проверенного изменения. Дважды в неделю короткое сведение команды по блокерам и зависимостям. Для каждого PR указывать ID задачи, наблюдаемое поведение, изменение, доказательства проверки и откат. Формат статуса — «ID · состояние · доказательство (коммит/CI) · следующий шаг · владелец · срок». После каждого окна из графика проводить ревью приёмки с QA. Для сетевого релиза дополнительно нужны подтверждения Security и Platform.
