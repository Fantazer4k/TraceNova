## Резюме для команды

TraceNova предоставляет открытый локальный API, который передаёт введённые идентификаторы внешним источникам и выполняет сетевые проверки от имени сервера. Главный риск при публикации — любой клиент с доступом к API может расходовать ресурсы сервера и квоты настроенных провайдеров. Второй риск — идентификаторы находятся в URL, ответы анализа не помечены `no-store`, а часть запросов к телефонным провайдерам выполняется с фиктивными ключами. До публикации нужны ограничения доступа и нагрузки, обновление зависимостей и ясные правила передачи данных провайдерам.

В текущей ревизии 15 локальных Python-тестов и два теста JavaScript прошли. Режим IP по-прежнему возвращает `pending`. Для телефонных, почтовых и username-источников остаются ошибки классификации результатов. Подтверждения эксплуатации у реального развёртывания нет.

## Область и правила проверки

- Объект проверки — локальная копия TraceNova и вызовы приложения через ASGI в памяти. Адрес развёрнутого сайта, тестовые учётные записи и матрица ролей не предоставлены. Активный продукт не реализует вход, сессии и роли. Секреты провайдеров авторизуют исходящие запросы приложения и должны проверяться на отдельном контуре.
- Использованы статический обзор потоков данных и мест вывода, анализ границ доверия, локальные позитивные и негативные проверки с заглушками и сверка выбранных пинов с бюллетенями сопровождающих. Трафик на сайты провайдеров, нагрузочные прогоны, активные сканеры и эксплуатационные проверки не выполнялись. Снимки экрана отсутствуют. Техническое приложение содержит безопасные запросы и команды для проверенных сценариев.
- Для будущей проверки развёртывания зафиксировать точные адреса и владельца, окно, лимит запросов, отдельные ключи и синтетические данные, контакт для остановки. Роли и тестовые аккаунты потребуются после появления аутентификации или если доступ ограничивает внешний шлюз.

| Правило | Состояние и условия допуска |
|---|---|
| Письменное согласие | Для локального обзора использован предоставленный репозиторий. Для сетевой проверки владелец должен письменно согласовать точные URL, API, аккаунты и допустимые методы. Перечень развёртываний, окно и запретные интервалы пока не согласованы. |
| Исключённые среды и действия | Staging, production, инфраструктура провайдеров и реальные пользовательские данные исключены из выполненной проверки. В локальном контуре использованы чтение файлов, вызовы ASGI без сети и заглушки. |
| Инструменты и ограничения | Для повторной проверки согласовать инструмент, предельную частоту, допустимые методы HTTP и предел параллелизма. Работу остановить при появлении реальных данных, непредусмотренного исходящего запроса или признаков деградации. |
| Обращение с данными | Тестировать с синтетическими идентификаторами. В доказательствах маскировать ключи, cookies, токены и реальные данные. До начала сетевой проверки согласовать доступ к материалам, срок хранения, удаление и контакт для уведомлений. |

## Техническое приложение

Инструменты — Git 2.52.0.windows.1 и ripgrep 15.2.0 для просмотра исходников, Python 3.13.13 с unittest и ASGI, Node.js 24.22.3 с VM и заглушкой DOM. Локальный Python запускался с FastAPI 0.109.0, Starlette 0.35.1, Uvicorn 0.27.0 и временным aiohttp 3.14.5. Исходный пин aiohttp 3.9.1 не проверен в этом запуске. Проверка бюллетеней выборочная, без полного SCA. aiohttp advisory по небезопасной десериализации относится к `CookieJar.load()`, вызова которого в приложении не обнаружено. Requests 2.31.0 входит в диапазон CVE-2024-47081. Прямых импортов Requests в исходниках не обнаружено. [aiohttp advisory](https://github.com/aio-libs/aiohttp/security/advisories/GHSA-jg22-mg44-37j8), [Requests advisory](https://github.com/psf/requests/security/advisories/GHSA-9hjg-9r4m-mvj7)

Из каталога `tracenova` наборы можно запустить следующими командами.

```sh
python -m unittest discover -s tests -v
node --test tests/test_rendering.cjs
```

Безопасные запросы для сверки локального контракта в памяти или на своей loopback-инстанции:

| Запрос | Результат |
|---|---|
| `GET /health` | HTTP 200 и JSON со статусом `ok`. |
| `GET /api/analyze?query=192.0.2.10&query_type=ip` | HTTP 200, `status: pending`, внешние запросы для этого режима отсутствуют. |
| `GET /api/analyze?query=example.com&query_type=unknown` | HTTP 400, `detail: Unsupported query type`. |
| `GET /` | HTTP 200, документ HTML. Проверить заголовки CSP и Referrer-Policy после исправления S4. |
| `GET /static/script.js` | HTTP 200, статический JavaScript. |

`test_api.py` воспроизводит проверку ошибки провайдера через заглушку и подтверждает отсутствие синтетического идентификатора в ответе и журнале. `test_rendering.cjs` проверяет выходную строку, работу URL-фильтра и сохранение безопасных ссылок. Для проверок S1 и S5 используйте синтетических провайдеров и утверждения о количестве вызовов и заблокированных назначениях.

## План исправлений

1. **До публикации.** Ограничить доступ, обновить зависимости, убрать фиктивные телефонные вызовы и проверить журналы прокси. Прогнать чистую установку и CI для поддерживаемых версий Python.
2. **Следующий спринт.** Ввести POST и `no-store`, применить квоты и предел параллелизма, добавить исходящие ограничения и защитные заголовки. Покрыть лимиты и статусы источников моками.
3. **После стабилизации контракта.** Реализовать IP и dual-stack DNS, показать покрытие и ограничения в карточках. Ввести метрики по режиму, провайдеру, задержке и типу сбоя без идентификаторов. Если появятся персональные кабинеты или сохранённые результаты, определить модель доступа, жизненный цикл сессий, MFA и хранение данных.
